    Product Discover Filter: Test Requirement Specification

    Repository: management-node Endpoint: POST /api/v1/product/discover/filter Role required: product_discovery Policy rule: policies.product.discover, reached via the route route-product-discover-filter (docker/opa/policies/routing/data.json) SPDX-License-Identifier: Apache-2.0 AND OGL-UK-3.0

    A formal test specification for a manual testing team, in the structure of product-discover.md. It states what the API does, what decides its behaviour, then gives numbered test cases (Objective / Preconditions / Test data / Given-When-Then), and finally the edge cases.

    Read together with product-discover.md

    This endpoint shares its request grammar, its validation, its policy rule and every refusal with POST /api/v1/product/discover. This document does not repeat discover's full operator matrix, its 400/403 catalogue, or its per-organisation entitlement reasoning - only what the filter panel adds: counts, value lists, and which filters are offered. Read discover's §2, §3, §5 and §7 first; this document cross-references them by test-case number rather than restating them.

    Product ids differ between environments (discover's product-id warning applies here too, but this endpoint never returns one). No expected value in this document is written in terms of an id.

    1. What the API does

    POST /api/v1/product/discover/filter returns the product catalogue's filter panel for one search: every filter the caller may apply, what it is, how it compares, and - where listing them is worth it - the distinct values it holds with how many products carry each one, for this request.

    It exists so a UI never has to guess the vocabulary or pay for it one value at a time. Before this endpoint, the catalogue UI hard-coded every field, attribute and value list (ui/src/vocabulary.js) and fired one discover call per value per group to get a count - 13 requests per refresh, and only for the four groups someone had written down. This endpoint gives the whole panel in one request, built from the same policy decision and the same search criteria as discover, so the panel can never offer or count more than discover would return.

    Three things follow from "built from the same decision as discover":

    Question Answered the same way discover answers it
    May this caller search at all? the product_discovery role, then the policy's caller gates
    Which products exist for this caller? the policy's row_filter; this is what every count is computed under
    What may be asked, and what is shown? the policy's allowed / masked lists decide which filters appear at all

    The filter permission decides what appears here, not result visibility. An attribute the contract lets the caller filter on is listed with its values and counts even when policy hides that block from the caller's own discover results - BCC (OFFICIAL) sees quality_designation and record_unit values in its panel although its own products' policyAttributes block is masked in discover's response. This discloses nothing discover does not already answer through totalElements: BCC could already learn the same counts by sending discover once per value. The panel answers it in one request instead. See TC-09.

    2. What governs it

    The same four gates as discover, with one difference in how the fourth is resolved:

    # Gate Refusal
    1 Authentication: a valid bearer token 401
    2 Authorisation: the product_discovery role 403 "Access denied: insufficient permissions for this operation"
    3 Request binding and bean validation (@Valid on the body) 400
    4 Policy: product.discover_filter → routed to policies.product.discover 403 "Access denied by policy" with reasons
    5 Criteria validation inside the handler 400 "Invalid search criteria: …"

    The handler is annotated @Policy(resource = "product", action = "discover_filter", details = ProductDiscoveryPolicyDecisionDetails.class). There is no policies.product.discover_filter module; an entry in docker/opa/policies/routing/data.json sends the action to policies.product.discover instead:

    {"id": "route-product-discover-filter", "resource": "product", "action": "discover_filter",
 "policy": "product.discover", "priority": 10, "enabled": true}

    This matters for two things a tester should expect:

    • Provenance differs from discover's even though the rule is the same. policy.resolution is route here, exact on discover, and policy.id is product.discover on both. A log line can therefore tell the two endpoints apart even though one rule answers both.
    • A caller gets the identical allow/deny verdict and the identical contract POST /api/v1/product/discover would give the same token the same body, because it is the same rule seeing the same input, module for module. dispatch_test.rego's test_discover_filter_is_routed_to_the_discover_rule asserts exactly this at build time.

    Everything else in discover's §2 applies unchanged: the calling organisation comes from the token's organisation claim, never the body; OPA fails closed.

    3. The request

    Identical to discover's: ProductDiscoveryRequestDTO, the same text, filters, sort, page and size members, the same limits, the same operators, the same default-operator rules. See discover §3 for the full table.

    Two members are accepted but have no effect here:

    Member Effect on discover Effect on discover/filter
    text the free-text condition drives counts (narrows every group as a request filter would) and enables/disables textSearch
    filters the WHERE clause drives counts, each excluded from its own target's counts (see counting rule)
    sort the ORDER BY accepted, validated identically, then ignored - there is no page to order
    page, size paging accepted, validated identically, then ignored - there is no page to return

    sort, page and size are still validated exactly as discover validates them (an invalid direction is still a 400), because validation and the policy decision happen before the service knows which members it will use. See TC-16.

    This is a real response: ENV, posting {"filters":[{"field":"organisation.key","values":["ENV"]}]} (filters[] abbreviated to three of its twelve entries for ENV; see §6 and TC-07 for the full derivation).

    totalElements

    How many products match the whole request - text, every filters[] entry, under the caller's row filter. Exactly what page.totalElements of POST /api/v1/product/discover would report for the identical body and token. See TC-04.

    textSearch

    { "enabled": true, "fields": ["name", "displayName", "description"] }
    • enabled: whether the caller may send text at all - contract.textSearchFields() non-empty.
    • fields: the fields a term is matched against, same list, same order, as discover's policy.textSearchFields.

    fields is [] and enabled is false only for a caller whose policy masks every text-searchable field - the same condition discover's TC-35 covers, which no shipped organisation triggers without editing the policy.

    filters[]

    One entry per filter the caller may use, in this fixed order: fields in ProductField declaration order (never id - see the note under §5), then product attributes sorted by label (case-insensitive), then organisation attributes sorted by label. A filter the contract does not permit (masked, or not in the allowed list) is not in the array at all - there is no "disabled" entry.

    key, target, label, dataType, multiValued, operators, defaultOperator, sortable

    These eight describe the filter itself, independent of the request; two callers with the same entitlement get byte-identical values for all eight, whatever criteria either one sent.

    Member Meaning Field example Attribute example
    key stable id for UI state field:format attribute:product.quality_designation
    target copied verbatim into a discover filters[] entry {"field": "format"} {"scope": "product", "attribute": "quality_designation"}
    label caller-facing name "Format", a fixed label per field (§5.1) policy_attribute_definition.display_name, e.g. "Quality designation"; falls back to the bare name when none is set
    dataType TEXT, NUMBER or BOOLEAN ProductField.Kind the definition's data_type, mapped (STRING→TEXT; no NUMBER or BOOLEAN attribute exists in the sample data)
    multiValued can the target carry more than one value at once always false, except subscribedBy the definition's multi_valued flag
    operators comparisons this target accepts, by wire name the field operator set (§5.1) minus whatever discover would refuse the attribute operator set (§5.2), all_of added when multi-valued, ordering operators added when dataType is NUMBER
    defaultOperator what the UI should send for a value pick contains for name/displayName/description; eq for the boolean isOwnProduct; any_of for the multi-valued subscribedBy; in for every other listing field eq for a boolean attribute (none exist); any_of when multi-valued; in otherwise
    sortable may the caller sort on this target in POST /api/v1/product/discover ProductField.isSortable() - false for description and subscribedBy always true

    operators must never offer something discover would refuse. subscribedBy's set has no contains (discover never accepts it there); every multi-valued attribute's set gains all_of; a NUMBER attribute's set gains lt/lte/gt/gte. See §5 for the complete per-target tables.

    values[]

    Present on every entry the panel offers. The three prose fields that would otherwise carry no values (name, displayName, description) are not offered in the panel at all (see the §5.1 note), and topic and source are excluded for the same reason, so no entry in filters[] lacks values any more. Each entry:

    { "value": "CSV", "count": 1, "selected": false }
    • value: a string, or a JSON boolean for isOwnProduct. Reported as stored ("CSV", not "csv").
    • count: how many products satisfy the counting rule for this value.
    • selected: true when the caller's own request already has an eq, in or any_of filter on this exact target naming this value, compared the way discover matches that filter: case-insensitively for a field (discover compares fields with LOWER(), so csv selects CSV) and exactly for an attribute (discover matches attributes with a.item IN (...), so Anonymised does not select anonymised). A neq, contains, exists or any other operator narrows the other groups but never marks a value selected - the request did not pick that value, it excluded or tested for others.

    Which values are listed is decided once, by the row filter alone - ignoring the request's own filters and text entirely: the distinct values held by at least one product the caller can see at all. Narrowing the request narrows counts, never the set of rows shown; see TC-07. A value no visible product holds is never listed, even when a policy_attribute_definition declares it in allowed_values - rare_condition_cohorts is a declared value of population_risk_tags that no sample product carries, and it never appears; see §6.

    Ordering: count descending, then value ascending case-insensitively; capped at 50 (§truncated). isOwnProduct is the one exception: always exactly true then false, in that order, whatever their counts, because there are only ever two.

    Case merging applies to fields, never to attributes. format values compare case-insensitively in the database (LOWER(p.format) IN (...)), so CSV and csv would be one row at search time; the panel merges them the same way, summing their counts under the spelling with the most products (ties broken by the lexicographically smaller spelling). An attribute filter compares exactly (a.item IN (...)), so validated and Validated would be two different rows to discover, and the panel lists them as two distinct values too - never merged. The sample data happens to be consistently cased, so this only shows up if a row is edited to differ; it is exercised directly in FacetValuesTest.

    missingCount

    How many products in the narrowed set (the whole request, minus this target's own filters - see the counting rule) have no value at all for this target: what a not_exists filter on it would match. Present only alongside values, and omitted - not 0 - when it would be zero, matching the rest of the API's "absent, never a zero default" convention.

    truncated

    true, and present, only when more than 50 distinct values existed for this target and the list was cut to the 50 most-matched. Omitted - not false - otherwise. No shipped sample attribute or field has more than a handful of distinct values, so every example in this document is untruncated; exercising truncated: true needs seeded data with 51+ distinct values for one target (see FacetValuesTest for the unit-level proof the cap and flag are applied).

    policy

    The identical object POST /api/v1/product/discover returns in its own policy member - same builder, same contract (ProductDiscoveryServiceImpl.policyBlock). Present only when policy enforcement is on; absent (not null) when application.opa.enabled=false. See discover's §4 "The policy block" and TC-17.

    The counting rule

    This is standard disjunctive faceting, stated once in the design and reproduced here because every test case in §8.B depends on it:

    A value's count is the number of products that satisfy the policy's row filter, the request's text, and every request filter except those on this same target, and that hold the value.

    Two things fall out of that sentence that are easy to get backwards:

    1. A target's own filter never narrows its own counts. Choosing organisation.key = ENV narrows every other group (format, type, every attribute) to ENV's products, but the Organisation group keeps showing what BCC's and HEG's counts would be if the caller switched
    2. that is the whole point of a facet panel: it tells you what picking something else would give you, not just what you already picked.
    3. Every other filter and the text term still apply, including filters on other targets. Several filters on one target are all excluded together from that target's own counts (picking two values of type does not stop the Type group reporting what a third value of type would give).

    Worked example, ENV posting {"filters":[{"field":"organisation.key","values":["ENV"]}]} (the response shown in §4 above):

    Group Own filter excluded from its own count? Narrowed by the organisation.key=ENV filter? Result
    Organisation yes - it is this group no unchanged from the baseline {} panel: ENV:6, BCC:5, HEG:4
    Format n/a - no filter on format yes ENV's 15-product baseline (CSV:4, JSON:4, Avro:1, GeoJSON:1, NetCDF:1, RDF:1, XML:1, missingCount:2) narrows to ENV's own 6: CSV:1, GeoJSON:1, JSON:1, NetCDF:1, XML:1, Avro:0, RDF:0, missingCount:1
    Type n/a yes baseline topic:8, file:6, missingCount:1 narrows to topic:3, file:3, missingCount:0
    totalElements n/a yes 15 → 6

    RDF and Avro staying in the list at count: 0 is the value-listing rule in action: both are values held by a product ENV can see but does not own (ScotlandLandRegisterExtract and HelpToBuyApplicants, both HEG's), so they are listed, even though no product in the narrowed set (ENV's own 6) holds either. The UI greys them out rather than removing them, so switching the organisation filter back off does not make the group's rows jump around.

    5. Critical fields

    Everything here mirrors discover's §5 exactly - the panel offers nothing discover would refuse and withholds nothing discover would accept - with the operator, label and default-operator mechanics this endpoint adds on top.

    5.1 Product fields

    Only six of the eleven filterable product fields are ever offered in the panel at all; the other five are filterable on POST /api/v1/product/discover exactly as before, but FilterOptionTargets.isOfferedInPanel excludes them from filters[] unconditionally, before the contract is consulted - so even a caller whose contract would permit them never sees them here. Being left out this way is a third reason an entry can be absent, alongside "not in the caller's allowed list" and "masked", and unlike those two it does not depend on the caller at all.

    API name dataType multiValued operators defaultOperator offered in panel? lists values? label
    id — — — — never (policy or no, see note below) — —
    name TEXT false 9: eq, neq, in, not_in, any_of, none_of, contains, exists, not_exists contains never - prose, already searched by textSearch — —
    displayName TEXT false same 9 contains never - prose, already searched by textSearch — —
    description TEXT false same 9 contains never - prose, already searched by textSearch — —
    topic TEXT false same 9 in never - an identifier nobody browses by — —
    source TEXT false same 9 in never - an identifier nobody browses by — —
    type TEXT false same 9 in when permitted yes Type
    format TEXT false same 9 in when permitted yes Format
    organisation.key TEXT false same 9 eq when permitted yes Organisation
    organisation.name TEXT false same 9 eq when permitted yes Organisation name
    subscribedBy TEXT true 8: eq, neq, in, not_in, any_of, none_of, exists, not_exists (no contains) any_of when permitted yes Subscribed by
    isOwnProduct BOOLEAN false 8: eq, neq, in, not_in, any_of, none_of, exists, not_exists eq when permitted and the caller's organisation is known yes, always both true/false My organisation's products

    id is never a filter option, whether or not policy is enforced. FilterOptionTargets excludes ProductField.ID unconditionally, before consulting the contract at all. This is stricter than "allowed − masked": with policy switched off, discover's own open contract would in fact accept a filter on id (contract.mayFilterOn returns true for every target when enforcement is off), but the filter panel still never lists it as an option in that state. This is a deliberate implementation choice beyond what the design note ("id never appears while policy is enforced") states outright - see the report accompanying this document.

    name, displayName, description, topic and source are never filter options either, for the same unconditional reason as id. FilterOptionTargets.isOfferedInPanel leaves them out before the contract is consulted, whether or not the caller's contract would otherwise permit them: the first three are prose already covered by the free-text box (textSearch), and the last two are identifiers nobody browses a value list for. Discover itself is unchanged: a caller who names one of these five directly in POST /api/v1/product/discover's filters[] is answered exactly as before, and each still appears in policy.filterableFields - only the panel stops offering it. See TC-02.

    Because the six remaining fields all list values when they are offered at all, every entry filters[] now carries, values is present on every one of them - there is no field entry without values any more. (An attribute entry always listed values already; see §5.2.)

    5.2 Policy attributes

    Attribute Scope dataType multiValued operators defaultOperator label (from display_name)
    record_unit product TEXT no 9 (as topic above) in Record unit
    identifiability product TEXT no 9 in Identifiability
    quality_designation product TEXT no 9 in Quality designation
    temporal_resolution product TEXT no 9 in Temporal resolution
    population_risk_tags product TEXT yes 10 (9 + all_of) any_of Population risk tags
    coverage_jurisdictions product TEXT yes 10 any_of Coverage jurisdictions
    jurisdictions organisation TEXT yes 10 any_of Jurisdictions
    responsibility_areas organisation TEXT yes 10 any_of Responsibility areas
    authorised_classifications organisation TEXT yes 10 any_of Authorised classifications
    permitted_purposes organisation TEXT yes 10 any_of Permitted purposes
    department_id organisation TEXT no 9 in Department id
    nationality organisation TEXT no 9 in Nationality

    No sample-data attribute is NUMBER or BOOLEAN, so no attribute in the shipped catalogue carries an ordering operator (lt/lte/gt/gte) or the boolean operator set; both are exercised at the unit level only (FilterOptionTargetsTest).

    None of these twelve is automatically a filter option. Whether one appears in a given caller's filters[] is decided the same three ways discover decides policy.filterableAttributes:

    Reason an attribute is absent from the panel Example, enforced
    not in the caller's allowed_filtered_attributes coverage_jurisdictions, department_id, nationality - absent for every organisation, none permits them
    masked for this caller (allowed − masked) n/a for attributes in the sample policy - no organisation's allowed list and masked list overlap today, unlike fields (source for BCC)
    flagged sensitive in the catalogue, while mask_sensitive_attributes is on population_risk_tags for HEG and BCC (below SECRET); authorised_classifications and permitted_purposes are sensitive too, but neither is in any organisation's allowed list regardless

    organisation.jurisdictions and organisation.responsibility_areas are the only attributes every sample organisation may filter on; see §6 for the per-organisation panel.

    5.3 Which filters appear, and in what order

    Reproduced from the design, ground-truthed against FilterOptionTargets.permitted:

    1. ProductField members that are filterable, offered in the panel (isOfferedInPanel - never id, name, displayName, description, topic or source, §5.1), and permitted by the contract, in declaration order.
    2. Product-scoped attributes permitted by the contract, sorted by label (case-insensitive).
    3. Organisation-scoped attributes permitted by the contract, sorted by label (case-insensitive).

    6. Test data

    The catalogue, the three organisations, their clearances and purposes, and every attribute value are exactly discover's - reproduced in full in product-discover.md §6. This section adds only what that one does not need: product format, and the panel each organisation is given.

    6.1 format, by product

    Set by src/main/resources/db/samples/V20261018121000__add_sample_product_display_names_and_formats.sql (the same migration TC-47/TC-48 of discover's spec exercise through displayName). UnclassifiedDraftDataset and Bristol_Cycle%Counts have neither a displayName nor a format.

    Product Owner format
    FloodRiskMapZones ENV GeoJSON
    RiverLevelTelemetry ENV JSON

    B. Narrowing and the counting rule

    TC-05: Each field and attribute group's values are the caller's whole visible set

    Objective. Confirm which values are listed is independent of the request's own filters.

    Preconditions. P1–P4.

    Test data. {} and {"filters":[{"field":"type","values":["topic"]}]}, both as ENV.

    Given ENV's 15 visible products, of which 6 have type=topic When the format group is read from both responses Then both list the same seven distinct format values (Avro, CSV, GeoJSON, JSON, NetCDF, RDF, XML) - the second response's counts are lower, but no value is added or removed.

    E1 A declared value no visible product holds {} as ENV, inspect attribute:product.population_risk_tags rare_condition_cohorts is absent from values, although it is a declared allowed_values entry listing a declared-but-unused value would disclose the vocabulary rather than the data, which TC-22 of discover's spec specifically guards against for filtering; the panel must not reopen that gap for listing
    E2 A target with no permitted values at all narrows to nothing an attribute filter that matches zero products, e.g. {"filters":[{"attribute":"record_unit","values":["spaceship"]}]} as ENV 200, totalElements: 0, every other group's counts all zero, every value still listed mirrors discover's TC-22: an unknown value is data, not an error, and the panel must not drop rows just because nothing currently matches
    E3 Metacharacters in text {"text":"%"} as BCC 200, totalElements: 0, every count zero the term is bound as a value in the facet query exactly as in the count query (TC-13)

    E7 The same request posted twice any body, twice, same token byte-identical responses counts are a pure function of caller, body and the catalogue's current state
    E8 A caller holding the role but failing policy's organisation gate a token with product_discovery but no organisation claim, policy on 403, reasons: ["organisation.missing"] - the same gate discover's TC-39c hits, since the decision is taken before either service runs this endpoint cannot be used to get a panel for an unidentified caller while policy is enforced; TC-12 is the one state (policy off) where that is even observable

    Things that should never happen

    1. A 500 from any input in this document.
    2. filters[] containing field:name, field:displayName, field:description, field:topic or field:source for any caller, policy on or off (§5.1's unconditional exclusion) - or field:subscribedBy for BCC, or attribute:product.population_risk_tags for HEG or BCC, while policy is enforced.
    3. A value listed in values[] that no product the caller can see actually holds.
    4. totalElements here differing from POST /api/v1/product/discover's page.totalElements for the identical body and token.
    5. A policy key present while application.opa.enabled=false, or absent while it is true.
    6. A reason beginning policy. or dispatch. in a response body (same rule as discover).
    7. The Organisation group's own counts changing when an organisation.key filter is added to the request (TC-07) - that is the one group a request can never narrow with its own choice.
